# Figures: Experiment 1 on the cluster (node13 VM)

Generated by `experiments/plots.py` from runs in one Ubuntu 24.04 KVM VM on node13
(12 vCPUs, 16 GB), one stack at a time (`cluster/vm/`):
- **Conductor + faasd:** `exp1-conductor-20260929-135611`, 20 runs. Conductor OSS 3.32.5, built-in SQLite
- **Argo + Knative, 10 s requeue (Argo's default):** `exp1-argo-20260929-213732`, 20 runs
- **Argo + Knative, 2 s requeue:** `exp1-argo-20260929-234613`, 20 runs

All 60 runs completed with reward 1. Same function images and mock LLM
(2 s / 2 s / 1 s per planner / actor / evaluator call) on every stack.

```bash
python experiments/plots.py --conductor experiments/results/exp1-conductor-20260929-135611 \
    --argo experiments/results/exp1-argo-20260929-213732 \
    --argo-tuned experiments/results/exp1-argo-20260929-234613 --out experiments/plots/cluster
```

| Figure | Main finding (medians) |
|---|---|
| `fig1_te2e` | Te2e: Conductor 56 s / 73 s (retail-44 / airline-26); Argo 315 s / 381 s at the default requeue, 130 s / 155 s at 2 s. Argo is 5.6× slower out of the box, 2.1× when tuned |
| `fig2_breakdown` | On Conductor, LLM time is 81–85% of a run. On Argo, orchestration is 85% at 10 s requeue and 62–63% at 2 s |
| `fig3_torch_per_turn` | orchestration per loop turn: 1.57 s (Conductor) vs 51 s (Argo, 10 s) vs 15 s (Argo, 2 s). Argo's values cluster at multiples of its requeue period |
| `fig4_timeline` | the median retail-44 run: Conductor runs the calls back to back; Argo leaves gaps between calls that shrink, but don't disappear, at 2 s requeue |
| `fig5_route_ecdf` | actor → tool routing: 23 ms through the faasd gateway vs 12 ms through Kourier + queue-proxy |
| `fig6_sworkflow` | Conductor keeps 3.1–3.3× more state per run (293 / 513 KB vs 89 / 163 KB); identical to the laptop, as expected |
| `fig7_rfriction` | Rfriction 0.19 (Conductor) vs 5.61 (Argo, 10 s) vs 1.71 (Argo, 2 s); 100% task success on all three |
| `fig8_torch_by_turn` | orchestration per turn stays flat over the loop on all three: it doesn't grow with the agent's history |

## Compared with the laptop (WSL2) runs

- **Routing reversed.** On the laptop, Knative's tool-call routing was 127 ms vs faasd's
  20 ms. On the cluster it is 12 ms vs 23 ms. The laptop's k3s ran with a DNS workaround
  (see `argo-knative/README.md`), which inflated every Knative call. The cluster figure
  is the one to trust.
- **Conductor's orchestration per turn is higher** (1.57 s vs 0.75 s). The cluster uses
  a newer Conductor (3.32.5) on its built-in SQLite store, where the laptop used a
  different setup. Compare stacks within one machine only.
- **Both requeue settings were run** under the same conditions, so "out of the box" and
  "tuned" Argo can both be reported.
