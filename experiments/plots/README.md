# Figures: Experiment 1 (Conductor + faasd vs Argo + Knative)

Generated by `experiments/plots.py` from:
- **Conductor + faasd:** `exp1-conductor-20260927-110845`, 20 runs
- **Argo + Knative:** `exp1-argo-20260927-181019`, 15 runs, default 10 s requeue

Each figure is saved as PNG (slides) and PDF (paper). Both stacks ran the same function
images, the same mock LLM (2 s / 2 s / 1 s per planner / actor / evaluator call) and the
same loop.

```bash
python experiments/plots.py --conductor <conductor results dir> --argo <argo results dir> \
    [--argo-tuned <argo 2s-requeue results dir>] --out experiments/plots
```

`--argo-tuned` adds a third series, in aqua, for runs with a tuned requeue time.

| Figure | What it shows | Main finding |
|---|---|---|
| `fig1_te2e` | end-to-end latency of every run, per workload | Argo + Knative takes ~5.5× longer: 294 s vs 53 s (retail-44), 337 s vs 64 s (airline-26) |
| `fig2_breakdown` | each run split into LLM time, function work, routing and orchestration | on Conductor, LLM time is ~88% of a run; on Argo, orchestration is ~82% |
| `fig3_torch_per_turn` | orchestration time per loop turn, log scale | median 0.75 s (Conductor) vs 41 s (Argo), ~55×. Argo's values cluster at multiples of 10 s, its default requeue period |
| `fig4_timeline` | the median retail-44 run, one bar per function call | Conductor runs the calls back to back. Argo leaves ~10–30 s gaps between them, even though the calls themselves take the same time |
| `fig5_route_ecdf` | routing time of every actor → tool call | median 20 ms through the faasd gateway vs 127 ms through Kourier + queue-proxy |
| `fig6_sworkflow` | state each orchestrator keeps per run, by kind | Conductor keeps 3–3.3× more (293 vs 89 KB, 513 vs 163 KB): it stores every helper task's data and a definition copy per task |
| `fig7_rfriction` | Rfriction per run, and task success | 0.11 vs 4.97. Both stacks completed 100% of runs |
| `fig8_torch_by_turn` | orchestration time by loop turn | flat on both stacks: overhead doesn't grow with the agent's history at these sizes |

## Notes for the write-up

- **Argo's Te2e comes from the Workflow's own timestamps.** Run `181019` was stopped before
  its driver wrote the CSVs, so its metrics were rebuilt with `recompute_dataplane.py`.
  Te2e is Workflow creation → finish, which Kubernetes records to the second (±1 s on
  ~300 s runs).
- **Argo's task success is inferred.** Its reward comes from the final verdict and answer,
  because the tool database couldn't be re-checked afterwards. Conductor's reward was
  scored by the driver.
- **Argo's orchestrator → function routing is estimated.** For those hops it uses the same
  run's median tool-call Troute (see `experiments/dataplane.py`). Tool-call routing
  (fig 5) is measured on both stacks.
- **Different k3s DNS settings.** The Argo runs were on k3s with the DNS workaround in
  `argo-knative/README.md`, which may inflate Knative's tool-call routing slightly.
